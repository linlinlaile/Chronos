## Context

The maintained application is the Python entry point `main.py`, its `actions.py`, `browser/`, `config.py`, and the offline tests. The repository also tracks a Maven project, Spring/WebMagic source, IntelliJ metadata, generated bytecode, debug captures, and runtime JSON state. The active main loop uses catalog-based credit-efficient selection, while older random and shortest-course entry paths remain defined but are not imported or called by production code.

The working tree can contain user-owned changes, especially `learned_courses.json`, and an untracked `CrawLearning/` directory. Cleanup must work around these files rather than deleting or reverting them.

## Goals / Non-Goals

**Goals:**

- Make the tracked repository represent the maintained Playwright application only.
- Remove Python code only when it is unreachable from production entry points and not required by retained behavior.
- Preserve the current CLI, browser session, course catalog, learned-course compatibility, playback monitoring, and failure handling.
- Leave a repeatable verification trail through reference searches, tests, syntax checks, and OpenSpec validation.

**Non-Goals:**

- Redesigning the active main loop or splitting modules into a new architecture.
- Changing course-selection policy, playback speed, learning verification, selectors, or retry limits.
- Deleting local browser profiles, learned-course history, course catalogs, or untracked user directories.
- Replacing Playwright or introducing direct platform API calls.

## Decisions

1. Classify cleanup targets before deletion. A tracked path is legacy when it has no import, invocation, build, documentation, or launcher relationship to the Python application. This supports removing `pom.xml`, `src/`, obsolete root `README`, and tracked `.idea/` metadata as one historical application boundary. The alternative of retaining them in an `archive/` directory was rejected because Git history already preserves them and an archive would continue to burden searches and reviews.

2. Treat untracked `CrawLearning/` as user-owned and out of scope. Its name suggests another copy of the historical project, but untracked content cannot be assumed disposable. The implementation may report it but must not remove or modify it.

3. Prove Python dead code from production reachability, not function age or test coverage alone. Start from `main.py`, launcher imports, and callbacks registered by active functions; remove a helper only when no retained production path reaches it. Tests dedicated solely to a removed path are removed, while tests covering shared helpers or active behavior remain. This is preferred over wholesale rewriting because the site automation contains hard-won compatibility behavior.

4. Separate repository untracking from local data deletion. Generated bytecode and committed debug artifacts can be removed. Runtime JSON files should be ignored for future changes and removed from Git tracking without deleting the working copy when the implementation mechanism permits; existing file formats and loading behavior remain unchanged. The user's modified `learned_courses.json` must never be overwritten or reset.

5. Use layered verification. Static reference searches establish reachability, the existing offline suite protects behavior, Python compilation catches import and syntax damage, and strict OpenSpec validation protects the change artifacts. A real logged-in browser run remains a manual follow-up because it depends on external session state.

## Risks / Trade-offs

- [A dynamically referenced helper is mistaken for dead code] -> Search string-based and callback references in addition to direct Python calls, then run import, compile, and offline tests.
- [Removing legacy files discards something still useful] -> Limit removal to tracked files proven unrelated to the maintained launcher; rely on Git history for recovery and do not touch untracked `CrawLearning/`.
- [Ignoring runtime JSON hides useful sample data] -> Document generated file formats in `README.md` and keep loaders tolerant of missing files.
- [Tests pass while selectors fail on the live site] -> Preserve all active selector and playback branches; include a manual authenticated smoke run in the task list.
- [Cleanup overlaps user changes] -> Inspect `git status` before each deletion group and leave modified runtime state intact.

## Migration Plan

1. Capture the pre-cleanup tracked-file inventory, working-tree status, production reference map, and baseline test result.
2. Remove the verified historical tracked project and generated repository artifacts without touching untracked or locally modified user data.
3. Remove unreachable Python selection paths, then prune only their exclusive imports, constants, and tests.
4. Update ignore rules and documentation to define maintained source and runtime state.
5. Run reference searches, the complete offline test suite, Python compilation/import checks, and strict OpenSpec validation.
6. Review the final diff for accidental data changes. Rollback is a normal Git revert of source removals; local user state remains available because it is not deleted.
